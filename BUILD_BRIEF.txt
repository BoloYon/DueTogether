=================== PRODUCT SPECIFICATION ===================

DueTogether gives Florida Polytechnic students a place to find classmates,
study sessions, and project teammates, plus a private view of their own
Canvas coursework. Work and Social are distinct areas. The demo focuses
on Work, with a clearly labeled Social preview. Do not imply that the
Social preview provides a campus network unless that service exists.

Core demo: open Work Feed, discover a live study session and join, find a
classmate with overlapping free time, open a conversation, and ask to join
a project. Connect a Canvas account if available, show the calendar, and
turn an upcoming exam or quiz into a prefilled study-session draft.

The campus data layer is local. Sessions, posts, messages, invites, and
project requests persist on that device. There is no campus authentication,
remote database, push notification service, or cross-device messaging in
scope. Show simulated chat replies and invite acceptance for the demo using
clear language. Canvas REST reads may be real. Fixtures must work with no
token or network. Use fictional people, locations, and coursework in
fixtures. Record truthfully what is live, simulated, pre-existing, and
built during the event. Do not imply code was built during the event if it
was brought in earlier. The humans confirm the event's reuse and AI rules.

NAVIGATION AND SHARED VISUAL LANGUAGE

- Main tabs in this order: Feed, Partners, Projects, Calendar, Profile.
- Root routes or nested equivalents: /create, /session/[id],
  /person/[id], /chat/[id], /project/[id], /calendar/settings,
  /partners/find, /partners/availability, /partners/invite,
  /notifications, /profile/settings. Publish the exact paths in PLAN.md.
- /create accepts optional course and title and can select session, partner
  post, or project creation. A Canvas study action defaults to session.
  Preserve normal creation without these parameters.
- Use small reusable components, polished mobile spacing, light and dark
  themes, high contrast, readable labels, and safe-area-aware layouts.
  A restrained iOS-inspired design is fine. Use system body typography.
  Serif display headings are optional if already available offline. Keep
  the app usable on small phones and with larger device text.
- Minimum 44 point hit areas for primary controls. Give icon-only controls
  accessible names and expose selected, expanded, and disabled states.
  Empty, loading, offline and error states must explain what the user can
  do. Keep animations short, subtle, and compatible with reduced motion.
  Use a 6–10 px slide with a short fade where useful, about 150–200 ms.
  Avoid spring overshoot and large movements on open, close, or tab switch.

WORK FEED

- Keep Social / Work as a prominent filled switch. Default to Work. Social
  is a clearly labeled preview with light sample campus hangout content
  or a simple coming-soon state. Match the app's social-and-work identity.
- In Work, use a quieter compact List View / Graph View toggle. Default
  to List View. Remove the old category chips if present in the scaffold.
- Both views use these sections in this exact order:
  Happening Now, Due Soon, Coming Up, Partners Wanted, New Projects.
- List View has collapsible headers with chevrons and expanded state.
  Populated sections start open, and toggles are independent. Keep
  headings reachable even if empty. Keep Due Soon's See all navigation
  separate from the accordion target.
- Graph View uses a horizontal text-tab row with an underline for the
  selected section. No graph accordion. One graph visible at a time,
  initially Happening Now or the first populated section. Bring the active
  tab into view. The underline tabs must look different from both switches.
- Happening Now: all live study sessions/events represented in the campus
  model, based on startsAt <= now < endsAt. Feature the live session with
  the largest attendance, then list other live sessions. Show time left,
  location or online format, and attendance. Refresh time-based grouping
  while the Feed is open. Ended sessions leave both live and upcoming.
- Coming Up: future sessions, soonest first. A session must never appear in
  both sections. Open a session to see its host, attendees, capacity, and
  location. Join/leave, save/unsave, full, ended, and hosting states belong
  to one shared rules layer.
- Due Soon: next three upcoming dated assignments, quizzes, or exams within
  seven days in the list. See all goes to Calendar. Graph has Today,
  Tomorrow, Next 7 days filters. The graph may show more than the preview
  three. Use local calendar boundaries for Today and Tomorrow. Only the
  connected student's coursework is visible. A mock fallback must be
  labeled and must never masquerade as the connected student's calendar.
- Partners Wanted: recent partner posts by other students, newest first.
  Show course/topic, goals, and author. Connect opens or reuses a chat.
- New Projects: newest first. Show owner, roles, team size, pitch, and
  capacity. Ask to join and cancel a request from the actual shared state.

COURSE GALAXY GRAPH

- Derive nodes and links from the same records the list uses. No copied
  mock graph roster when real app state is available. Use stable IDs and
  one node per person, even if they connect several clusters.
- Silhouettes: large course/topic planet with a short code and name, small
  student moon with initials/name, rounded diamond for a session, circle
  with type icon for a Canvas item, capsule for a partner post, and rounded
  hexagon for a project. Make session diamonds visibly bigger than ordinary
  circular item and student nodes. Course planets may be larger anchors.
- Live diamonds have a readable red live indicator and attendee count.
  Upcoming diamonds have a date and no live indicator. Canvas urgency is
  a separate Today/Tomorrow/weekday label. More urgent items sit closer to
  their planet. Show a compact legend specific to the active graph.
- Relationships: item-to-planet, attendee-to-session, author-to-post,
  owner/team-member-to-project. In Partners Wanted and New Projects, show
  a distinctive solid line from You to known contacts. New-to-you people
  get a dashed outline and explicit label, without a line to You. Use real
  thread/connection state. Show pending only where the state truly supports
  it. A project request never makes someone a personal connection.
- Native renderer with react-native-svg. Prefer a small deterministic
  layout using anchored planets, springs, repulsion, label-aware collision,
  damping, and bounded positions. Place multi-course people near the
  relevant clusters. Account for diamond corners and labels in collision
  spacing and touch bounds. Avoid adding an unapproved dependency.
- Save selection and viewport per section while switching tabs. Preserve
  positions for unchanged IDs when an item or connection changes. Stop
  the force loop when settled, unfocused, or unmounted. Reduced motion
  settles immediately. Do not simulate hidden graphs.
- Tap to select, drag after a small movement threshold, pan, pinch zoom,
  and Fit View. Select highlights direct neighbors and dims other nodes.
  Make graph gestures cooperate with vertical Feed scrolling. Keep the
  graph a little shorter on phones so the content below can peek into view.
  Fit the graph to the measured stage, including outer labels.
- Put selected details below the graph on phones. Add an accessible node
  list or equivalent selection path. Put Join, Open in Canvas, Message,
  Connect and Ask to join in the details. A tap or drag on the graph must
  never dispatch those actions. A selection can open the appropriate detail
  route if needed. Reuse the normal app action and check the UI updates
  across both views.

PARTNERS, SESSIONS, CHAT, AND PROJECTS

- Partner search by course/topic and person. Display existing conversations
  in a Messages section. Profile links resolve by person ID.
- Connect carries the partner post ID. Find its author. If this is the
  first contact, create one thread for that person with an intro message.
  If there's already a thread, attach the new post as context and reuse
  it. The same post twice is a no-op. Expose multiple course/post contexts
  in the conversation. A connection belongs to the shared campus state.
- Chat has incoming/outgoing bubbles, course context if applicable,
  composer validation, timestamps, and a typing indicator for a simulated
  reply. Store queued reply text and due time centrally, not in the chat
  screen. Rehydrate it after relaunch and deliver once. Derive unread
  indicators from thread state. Keep simulations deterministic under test.
- Availability uses dated local windows with start/end minutes. Reject
  invalid or expired input, support edit/remove, normalize course codes,
  intersect windows on the same date, trim past portions, and sort matches
  by earliest remaining shared time. An invite has pending/accepted state.
  Simulated acceptance creates exactly one session with both attendees and
  a local notification. Use stable IDs and injectable clocks for tests.
- Session creation supports course or personal topic, start, duration,
  location/online format, capacity, and description. Validate before
  creating. Joining is idempotent and respects capacity and end time.
  Saving a session is independent from joining. Use immediate shared state
  updates so the Feed and detail page agree.
- Project list and detail show pitch, open roles, owner/team and occupancy.
  Support course or personal category. Project creation validates title,
  pitch, roles, and size. Ask to join marks Requested and offers cancel.
  It does not add a team member. Owners and existing members get the
  appropriate status; full teams cannot receive another local request.
- Profile shows editable name/major and sections for going/saved sessions,
  posts, and project requests. Reset demo data asks for confirmation and
  affects campus data only. Notifications support unread, mark read, mark
  all read, and opening the relevant route.

CANVAS AND CALENDAR

- Calendar Settings owns connection controls. Collect school Canvas base
  URL and a masked personal access token for the account holder's demo.
  Read CANVAS_BASE_URL from shared non-secret config as an optional default.
  Keep a placeholder empty until a verified school host is supplied.
  Validate HTTPS origin and reject credentials in the URL and non-HTTPS
  schemes. Make the destination clear before handing it a token.
- The demo's native app calls Canvas directly over HTTPS and uses a
  personal access token for the participant's own account. No public PAT
  onboarding and no OAuth implementation. Define a credential interface
  so a real authorization flow can be added later. Token instructions refer
  to Canvas Account > Settings > Approved Integrations > New Access Token
  where available. Never ask other students to hand over their tokens.
- Use GET only and Authorization: Bearer <token>. Verify the account with
  users/self, read active courses for names and codes, then read
  /api/v1/planner/items with explicit start_date and end_date. Default to
  120 days back and 180 days ahead. Follow Link rel=next only on the
  configured origin, reject redirects or otherwise prevent credentials
  crossing origins, handle cancellation, bound timeouts and paginate.
  Treat auth/rate/network/timeout failures distinctly. No token in logs,
  URLs, crash messages, fixtures, AsyncStorage, commits, or screenshots.
- A2 owns translation. Use course IDs to attach the name (nickname when
  returned) and code. Map the planner's actual plannable_type and supplied
  assignment/quiz metadata before falling back to title clues. Identify
  exams, quizzes, homework and dated calendar events where supported.
  Keep exact due/start/end timestamps, preserve all-day date strings, and
  skip records with no usable date. Preserve the specific Canvas item URL
  if safe and present. Stable IDs should include record kind and Canvas
  identifier; handle the same item on multiple pages and student-specific
  date overrides where identifiable. Never deduplicate by title alone.
- A valid new connection loads identity and an initial snapshot before it
  replaces any working connection. Store native tokens in SecureStore and
  store only non-secret settings plus coursework in AsyncStorage. Validate
  the cached snapshot account key (school origin + Canvas account ID).
  Cache scope and disconnect must prevent prior account data leaking into a
  replacement connection, even when a previous request finishes late.
- One calendar provider/adapter. Sync on initial load and foreground when
  stale (use five minutes as the default), coalesce concurrent refreshes,
  and support pull-to-refresh, Sync now, Last synced, Retry and Disconnect.
  Successful snapshots replace records within their query window and keep
  history outside it for the same account. A failure preserves the last
  good snapshot. Disconnect clears credentials and private cached items.
  When disconnected, offer a labeled sample calendar for a no-network demo.
- Calendar tab defaults to List and remembers the choice. List splits
  Upcoming/Past and groups by date. Past depends on the deadline or event
  end, not completion. Calendar view shows an actual month grid, weekday
  headers, previous/next buttons, Today, selected day, and item markers.
  Show selected-day rows below. Exams & quizzes filters both views.
  View/range navigation uses the cache and does not initiate a sync.
- Rows show title, class, date/time, and type. Optional LockDown tag comes
  from a recognized Respondus note, which can be removed from display title.
  Open in Canvas goes to the exact item URL if present. Study for this on
  exams and quizzes opens a prefilled session draft. Grades, submissions,
  and modifying Canvas coursework are outside scope.

=================== SHARED CONTRACT AND BASELINE ===================

Use one central src/shared directory. Types below specify the minimum public
contract. The coordinator may adjust naming once before the lanes launch,
then document the exact signatures in PLAN.md. Use strict TypeScript.
Date-time strings from Canvas remain ISO strings. Campus instant times
are numeric epoch milliseconds. Calendar day keys are YYYY-MM-DD strings.
All IDs are strings. Never use display names as identity.

  User { id, name, major?, year?, initials?, courses: string[] }
  Course { id, name, code? }
  CanvasItem {
    id, canvasId, courseId?, courseName, courseCode?, title,
    kind: 'homework' | 'quiz' | 'exam' | 'event',
    dueDate?, startsAt?, endsAt?, allDayDate?, htmlUrl?, lockdown?
  }
  CanvasSnapshot {
    accountKey, range: { start, end }, items: CanvasItem[], fetchedAt
  }
  StudySession {
    id, title, course?, topic?, hostId, attendeeIds: string[],
    startsAt, endsAt, createdAt, capacity?, location?, format?, description?
  }
  PartnerPost { id, authorId, course?, topic?, title, description, createdAt }
  Project {
    id, title, pitch, ownerId, teamIds: string[], openRoles: string[],
    capacity, course?, category?, createdAt
  }
  Membership { userId, projectId, status: 'requested' | 'member' }
  Thread { id, personId, postIds: string[], messages: Message[], readAt?,
    pendingReply?: { id, text, dueAt, course? } }
  Message { id, authorId, text, sentAt, course? }
  AvailabilityWindow { date, startMinute, endMinute }
  StudyInvite { id, personId, course, startsAt, endsAt, location?,
    status: 'pending' | 'accepted', acceptAt?, sessionId? }
  Notification { id, title, body, createdAt, read, href? }

Baseline files and module boundaries:
- src/shared/types.ts: all public entities, domain state and action types,
  raw Canvas transport shapes, connection results, and date range types.
- src/shared/config.ts: public defaults only, including CANVAS_BASE_URL,
  calendar sync window and refresh interval. No personal token.
- src/shared/mockData.ts: typed, deterministic campus fixtures using an
  injectable clock. Include connected and unfamiliar students, live/
  upcoming/ended/full sessions, multiple posts by one author, overlapping
  schedules, projects with mixed teams, and sample Canvas rows across a
  week. Existing deadline examples should remain useful on any demo date.
- src/shared/adapters.tsx: coordinator-owned adapter facade and reference
  mock implementations. Stable useCampus() and useCalendar() signatures
  let frontend lanes work immediately. Supply a typed testable provider
  injection seam so integration swaps providers without rewriting screens.
- src/shared/navigation.ts: stable route helpers or parameter types.
- Declare each lane module entry point and output shape in PLAN.md. Root
  integration is intentionally coordinator-owned. Lane code may exercise
  its own screens via unit/flow tests with injected adapters or a local
  harness inside its owned folder. Shared staging files are read-only.

Adapter contracts to freeze:
- useCampus(): current state and typed dispatch. State contains current
  user, people, sessions, saved session IDs, posts, post-to-thread map,
  threads, projects, memberships, availability, invites, notifications.
  Expose named commands/actions for each mutation in the product spec.
- useCalendar(): status, connection/account metadata excluding token,
  items, sample/live mode, lastSyncedAt, error, and commands connect,
  sync, disconnect, and enterSampleMode if supported. Keep raw tokens out
  of adapter state and out of React component props except transient form
  input passed to the connect command.
- Raw Canvas transport: getSelf, listCourses, listPlannerItems, plus a
  composed read function that returns account, courses and planner records.
  A2 injects a transport matching the contract; A1 implements it. Publish
  error codes, cancellation semantics, fixtures, inputs and outputs up front.
- Pure selectors: derive Feed sections, session state, due ranges, lookup
  thread by person, and find availability overlaps from passed state and
  now. Keep side effects out of selectors and state transition functions.
